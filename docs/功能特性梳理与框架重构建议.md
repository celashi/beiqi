# 功能特性梳理与框架重构建议

## 1. 当前功能特性（按用户视角）

### 1.1 手动移动
- 前端支持上/下移动按钮，并且支持长按持续触发移动请求。
- 后端 `/move` 接口会根据速度动态计算单次移动步长，并将动作放入指令队列串行执行。
- 在移动前会校验当前“实际间隙”，当间隙小于阈值时触发自动找零/释放逻辑，避免危险工况。

### 1.2 紧急释放（回零）
- 前端“紧急释放”按钮调用 `/home`。
- 后端会清空待执行队列并插入回零任务；若零点未建立，回零逻辑会自动先找零再回零。
- 系统启动时会先执行一次找零，确保零点有效后再开放服务。

### 1.3 自动循环
- 前端可配置间隙、速度、保持时间、循环次数并调用 `/cycle`。
- 后端会进行参数限幅，并执行“到目标位 -> 保持 -> 返回基准位”的闭环循环。
- 每次循环前都会再次检查间隙阈值，不满足时会触发自动找零并重置基准位后继续。

### 1.4 实时状态与进度
- 前端以固定周期轮询 `/position`。
- 页面显示“实际间隙”和“循环进度”，用于观察当前执行状态。
- 前后端都维护了“位置/间隙”概念，但计算口径存在分散。

### 1.5 急停硬件保护
- GPIO 按键中断触发急停事件（含防抖）。
- 独立监控线程接到急停后会立即停止电机、清空任务并提交回零任务。

## 2. 当前“杂乱/混乱”的根因（架构层）

### 2.1 单文件承载过多职责
`app.py` 同时承担：
- Flask 路由层
- GPIO 初始化与中断
- 电机运动控制
- 任务调度（队列+worker）
- 全局状态管理
- 安全策略（阈值保护/急停）

导致问题：
- 修改一个点容易影响多个领域。
- 可测试性差（很难只测路由/只测控制逻辑）。
- 新功能容易继续“堆”到同一文件。

### 2.2 共享全局状态较多，语义边界不清
- `current_position_mm`、`zero_position_established`、`cycle_progress`、`emergency_event`、`cmd_queue` 分散在全局。
- 状态读写在多个函数中交叉出现，依赖人工加锁保证一致性。
- “位置/间隙”的业务语义没有单独抽象，前后端各自计算，存在偏差风险。

### 2.3 安全逻辑分散在多个执行路径
- 移动逻辑、循环逻辑、接口入口都在做“间隙阈值检查”。
- 回零/找零与急停恢复路径互相调用，存在流程交织。
- 未来新增动作时，容易遗漏安全检查。

### 2.4 参数约束前后端不一致
- 前端对 `gap/hold` 的限制区间与后端限幅区间不完全一致。
- 这会产生“前端不让输但后端可执行”或“前端允许但后端被改写”的体验问题。

### 2.5 领域模型缺失
当前代码以“过程函数”为主，缺少明确对象边界：
- 控制器（Controller）
- 调度器（Scheduler）
- 状态仓库（State）
- 安全策略（SafetyPolicy）

因此读代码时很难快速回答“谁负责什么”。

## 3. 建议的重构目标（先稳再优）

### 3.1 明确分层
建议拆成最少 5 层：
1. **API 层**：只做参数解析、调用服务、返回结果。
2. **应用服务层**：编排动作（move/home/cycle/stop）。
3. **领域层**：运动原语、找零、循环状态机、安全策略。
4. **基础设施层**：GPIO、pigpio、电机驱动适配。
5. **状态层**：线程安全状态对象与事件。

### 3.2 安全策略集中化
把“阈值检查、急停状态、超限保护、恢复流程”收敛到一个 `SafetyManager`：
- 任何动作执行前统一 `precheck(action)`。
- 所有动作中断统一 `on_emergency()`。
- 避免在每个函数重复拼装安全逻辑。

### 3.3 任务模型标准化
把 `cmd_queue` 的 lambda 改成显式命令对象：
- `MoveCommand`
- `HomeCommand`
- `CycleCommand`
- `StopCommand`

收益：
- 更可追踪（日志可打印 command id）。
- 更可扩展（可实现优先级/取消/重试）。

### 3.4 状态模型收敛
使用一个线程安全状态对象（例如 dataclass + lock）承载：
- 当前位置、零点状态、循环进度、当前模式（Idle/Moving/Homing/Cycling/Emergency）
- 对外暴露只读快照，避免任意位置散写。

### 3.5 前后端参数协议统一
建议把参数边界定义在后端常量并通过 `/config` 下发给前端：
- 前端校验与后端一致，减少魔法数字。
- 后续调参只改后端即可。

## 4. 可落地的分阶段改造路线

### Phase 1（低风险，1~2天）
- 抽离配置常量到 `config.py`。
- 抽离全局状态到 `state.py`。
- 路由仅保留 I/O，业务函数迁移到 `service.py`。
- 不改业务行为，只做“同逻辑搬家 + 回归验证”。

### Phase 2（中风险，2~4天）
- 引入 `SafetyManager`，统一阈值与急停流程。
- 引入显式命令对象替换 lambda 队列。
- 对循环流程增加状态机（Idle/Approach/Hold/Return/Interrupted）。

### Phase 3（优化，持续）
- 增加模拟层（Mock GPIO / Mock Motor）用于离线测试。
- 补充单元测试与集成测试。
- 将前端 API 调用封装为统一客户端并接入 `/config`。

---

## 5. 你现在可以立刻执行的“捋顺动作”（不大改代码）

1. 先统一参数边界（前后端一致）。
2. 给所有动作增加统一日志字段（动作名、参数、开始/结束、耗时、是否急停）。
3. 先把状态读写集中到 2~3 个函数入口，减少散写。
4. 逐步把 `app.py` 按“路由/业务/硬件”拆文件。

这样做可以在不影响产线行为的前提下，先把“可读性”和“可维护性”拉起来，再逐步做深度重构。
